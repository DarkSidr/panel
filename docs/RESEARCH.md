## Потоки

TCP 443 → nginx stream → PANEL: локальный HTTPS nginx 7443 → панель 2053,
подписки 2096 и разрешённые HTTP-входы.
SITE → локальный сайт 9443, либо REALITY-inbound после его регистрации;
неаутентифицированный REALITY → target 9443, с PROXY v1.
UDP → nginx stream на внешнем IP → AWG loopback того же порта.

Неизвестный SNI → reject handshake. Неизвестный путь панели → 404.
Обычный сайт не содержит ссылок на панель, подписки или credentials.
Открытые сайты/сертификаты не гарантируют невидимость VPN и отсутствие блокировок.

## DIRECT и каскад

Первичная конфигурация использует проверяемые категории geoip:ru и
geosite:category-ru плюс доменные суффиксы ru/su/рф. Xray -test проверяет наличие
категорий на установленной базе до запуска. При ошибке установка останавливается,
а не запускает неправильную маршрутизацию. В отличие от geosite:ru, category-ru
соответствует используемому набору данных. Базы не являются полным реестром всех
российских ресурсов; правила дополняются владельцем.

API и блокировка внутренних IP идут раньше RU-правил. DIRECT/freedom выходит
с IP VPS; это не клиентский обход туннеля. Пока каскад не задан, default outbound
тоже direct. Для будущего каскада добавьте outbound с отдельным tag, оставьте
RU→direct, затем задайте явное правило остальных направлений на каскад после RU.
При отказе каскада не добавляйте автоматический fallback direct, если нужно
сохранить выбранный IP выхода. Не направляйте адрес самого exit-сервера в его
собственный туннель. Обрабатывайте DNS/IPv6 согласованно с выбранным маршрутом.
Firewall проекта не меняет OUTPUT, default route и kernel forwarding.

## WARP

В 3x-ui v3.11.0 есть штатный WarpService и /panel/api/xray/warp/:action.
Регистрацию и добавление outbound выполняйте через интерфейс панели: установщик
не регистрирует WARP, не принимает лицензионные условия от вашего имени и не
меняет сетевой маршрут VPS. Используйте отдельный tag, например warp.

Порядок правил: API → блок внутренних сетей → RU direct → выбранные сервисы warp
→ остальное direct или будущий cascade. Если правило WARP охватывает весь интернет,
оно всё равно должно идти после RU. Проверяйте реальный IP выхода отдельным своим
клиентом. WARP не гарантирует выход в определённой стране. Для двойного туннеля
cascade→WARP настройка должна выполняться на нужном выходном узле, иначе порядок
цепочки может оказаться обратным ожидаемому. Не запускайте сторонний warp-скрипт,
меняющий системный default route, поверх этой установки без отдельного анализа.

## Границы автоматизации

Синхронизация использует node-sync API token, поскольку monitor не разрешает
/inbounds/list. node-sync также имеет разрешения на изменение входов: токен root-only,
сервис читает входы/Hosts через GET и при включённой автонастройке один раз
настраивает новые VLESS-входы через POST /inbounds/update/:id. Существующие входы
при включении автоматизации помечаются как обработанные; их настройки сохраняются.
Публичный External Proxy для новых VLESS задаётся автоматически. Протоколы,
которым нужен отдельный адаптер, не публикуются универсальной прокладкой.
Многопользовательская статистика не заменяет проверку реального IP за relay.

AWG: фактический API возвращает streamSettings=null, а сохранение inbound
нормализует его в пустую строку. Для публичного endpoint AWG используется Hosts API
(`/panel/api/hosts/list`); эти же Hosts применяются генератором подписок.
Ядерный режим не поддерживает bind на loopback и не является заменой
userspace-адаптеру nginx. Установка DKMS для этой архитектуры не требуется.

## Несколько REALITY-транспортов

Официальный Xray v26.10.21 разрешает REALITY только для RAW, XHTTP и gRPC:
https://xtls.github.io/en/config/transports/reality.html
https://github.com/XTLS/Xray-core/blob/v26.10.21/infra/conf/transport_internet.go
PROXY header для XHTTP/gRPC принимается через sockopt.acceptProxyProtocol.
Проверено отдельными процессами nginx и Xray на loopback с существующим UUID/ключами,
без создания объектов панели: все три транспорта вернули HTTPS 200.
Поддержаны карты (публичный TCP-порт, SNI) → локальный backend. Сервис не может
выбирать REALITY-вход по HTTP-пути до расшифровки. Дополнительные имена требуют
DNS, включения в конфигурацию и сертификат; add-reality-name выполняет эти проверки
и расширение сертификата, но не редактирует DNS у регистратора.
